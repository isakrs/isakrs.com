What makes a
good data platform?

Teams can find the data they need, understand what it means, use it safely, and recover when something goes wrong.

By Isak Rathe Støre · Updated 12 November 2026 · About 14 minutes

A platform earns its place when it helps people ship something useful: an analysis they trust, a product feature, a forecast, or a reliable export to another system. I would judge it by the path from a producer’s data to that outcome.

This is my view of the engineering principles behind that path. The examples are fictional and simplified, rather than a copy of any employer’s production configuration. They make the operating model concrete without requiring you to know the tools first.

01 / START WITH THE USE

Follow one event all the way through.

Imagine a payment event. A product team creates it, a pipeline receives it, transformations give it a useful shape, and a consumer uses the result. The end might be a dashboard, a model, or a product team receiving an approved dataset.

Each handoff needs an answer to three questions: what does this data mean, who is responsible for it, and what can the next person rely on? A diagram that stops at “the data is in storage” leaves most of the useful work unexplained.

02 / MAKE THE NORMAL PATH EASY

Offer a small set of dependable services.

I want teams to spend their time on their domain, rather than relearning how to create a job, request access, or publish a dataset. A good platform makes common work repeatable through versioned templates, configuration, and clear defaults.

The service should say what it accepts, what it produces, and what the team still owns. “Publish a dataset” is a useful promise. “Here is a workspace; good luck” leaves every team to build its own platform.

Standardisation also needs an escape route. An unusual workload may need custom code or different compute. Make that exception explicit, with an owner and a maintenance plan, rather than letting it become a hidden dependency.

03 / WRITE DOWN THE RECIPE

YAML describes it. Terraform or OpenTofu builds it.

Think of a shared kitchen. A recipe says what to make, the kitchen supplies the equipment, and someone checks the recipe before it changes. On a data platform, YAML is the readable recipe: a text file of names, settings, and lists.

In this operating model, all jobs, infrastructure, and access rules are declared in YAML and kept in GitHub. Jobs say what runs and when; infrastructure says which storage and compute are needed; access rules say which identities may use which data. Terraform or OpenTofu is the infrastructure engine: platform modules read the YAML and use providers to manage cloud resources, Databricks jobs, and Unity Catalog grants. GitHub Actions runs that engine. Python and SQL still implement processing and models; YAML is the request format, not a replacement for infrastructure code.

Think of YAML as the order form, Terraform/OpenTofu as the builder, and GitHub Actions as the delivery schedule. The builder compares the desired setup with the existing one. A plan previews additions, changes, and removals; an apply carries them out. This makes a permission change something the team can review and reproduce.

For our payment example, the recipe asks for a daily calculation, a place to store its result, and read access for a reporting group and a reporting service.

See a small platform recipe in YAML

Illustrative platform-specific schema, not a built-in Databricks format. A platform needs a validator and deployment implementation for these fields.

# platform/daily-payments.yaml — fictional platform schema
name: daily-payments
owner: payments-team
infrastructure:
  storage: object-storage
  compute: small-job-compute
  catalog: published
  schema: payments
job:
  schedule: "0 6 * * *"  # Every day at 06:00
  time_zone: Europe/Oslo
  run_as: payments-transformer
  command: dbt build --select daily_totals
access:
  - table: published.payments.daily_totals
    group: payments-report-readers
    privileges: [SELECT]
  - table: published.payments.daily_totals
    service_principal: payments-reporter
    privileges: [SELECT]

The job’s run_as is its working identity. The reader identities are separate: permission to run a calculation and permission to read its result are different decisions. The transformer also needs explicitly configured input-read and output-write permissions, omitted here for brevity.

See the GitHub Actions workflow shape

A simplified OpenTofu workflow. Tool installation, federated authentication, provider versions, and a remote state backend are assumed configured. The validation script is a repository-owned entry point: it checks YAML and modules and produces the pull-request plan. It is not a built-in command.

# .github/workflows/platform.yml — illustrative workflow
name: Validate and deploy platform
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/validate-platform
  deploy:
    if: github.event_name == 'push'
    needs: validate
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      # Authenticate using a configured federated identity.
      - name: Plan and apply merged infrastructure
        working-directory: infrastructure
        run: |
          tofu init -input=false
          tofu validate
          tofu plan -input=false -out=deployment.tfplan
          tofu apply -input=false deployment.tfplan

Pull requests validate and preview changes without applying them. Merging to main starts the protected deployment job: it creates a fresh plan for the merged revision and applies that saved plan. A saved plan is tied to its configuration and state; do not reuse an older pull-request plan blindly. environment: production selects the environment whose protection rules are configured in GitHub. Federated authentication lets the deployment use a workload identity without storing a long-lived cloud password in the YAML. The environment gate controls entry to this deployment job; the pull request is where the proposed changes are reviewed.

Terraform/OpenTofu also keeps state: a record connecting declared resources to the objects it manages. Keep that state in a shared backend with locking and appropriate access controls, so concurrent deployments do not compete. Pin the engine and provider versions for each stack. The example uses tofu; Terraform uses the same plan/apply structure with the terraform command.

04 / GIVE EACH IDENTITY THE RIGHT KEYS

Finding a table is different from being allowed to read it.

Imagine a library: knowing a book is on a shelf does not give you a key to every locked room. Unity Catalog is the shared directory and permission system for data in Databricks. A table name such as published.payments.daily_totals gives its catalog, schema, and table: roughly a building, a room, and a named item.

To read that table, an identity normally needs USE CATALOG on published, USE SCHEMA on payments, and SELECT on the table. The first two let it use the containers; they do not by themselves grant permission to read the rows. Unity Catalog documents these privileges.

There are two approval decisions. A pull request approves what access the platform should offer. An access-management request approves which person should receive it, for what purpose and duration. We should be able to explain and audit both.

See YAML become Terraform-managed Unity Catalog grants

We manage access with the Databricks provider’s databricks_grants resource. The module reads a small YAML declaration and defines the permissions as infrastructure. Terraform/OpenTofu applies them through the provider.

Fictional names and simplified module. Provider authentication and existing catalog, schema, table, and group setup are omitted.

# access.yaml — fictional module input
catalog: published
schema: payments
table: daily_totals
readers_group: payments-report-readers
# access.tf — simplified platform module
locals {
  access = yamldecode(file("${path.module}/access.yaml"))
}

resource "databricks_grants" "catalog" {
  catalog = local.access.catalog
  grant {
    principal  = local.access.readers_group
    privileges = ["USE_CATALOG"]
  }
}

resource "databricks_grants" "schema" {
  schema = "${local.access.catalog}.${local.access.schema}"
  grant {
    principal  = local.access.readers_group
    privileges = ["USE_SCHEMA"]
  }
}

resource "databricks_grants" "table" {
  table = "${local.access.catalog}.${local.access.schema}.${local.access.table}"
  grant {
    principal  = local.access.readers_group
    privileges = ["SELECT"]
  }
}

USE_CATALOG and USE_SCHEMA allow use of the containers; SELECT grants table reads. These are provider privilege names, with underscores. The group receives the grants; approved people inherit them through membership.

The provider’s databricks_grants resource manages the full grant set for an object. A real module must collect all intended grants for that object in one place, including other readers and service identities; separate competing resources or out-of-band edits can overwrite one another. This example shows only the fictional reader group.

For direct service-principal access, a grant block uses the registered application identifier as its principal. For group-based access, it uses the account-group name. Databricks supports both patterns; the same reviewed infrastructure process manages the grants.

A service principal is an identity for software. An Azure managed identity is an Azure-managed workload identity that avoids an application-managed password. It still needs supported authentication, provisioning, and explicit permissions to use Databricks. A managed identity used by a storage connector to reach cloud files is a separate role from the identity running a data job. Neither is an automatic pass to every table.

Unity Catalog grants also do not replace workspace, compute, cloud-storage, or destination-system permissions. An export may need to read a source table and write to a destination database. Declare and verify each part. Removing one group membership does not revoke access obtained through another group or a direct grant; inspect the identity’s effective access.

05 / MAKE TRUST INSPECTABLE

A green job is only the beginning.

A pipeline can finish successfully while delivering duplicate events, stale data, or the wrong business definition. Trust needs evidence at the point where somebody consumes the result.

For the payment example, I would ask whether the event identifier is unique, the amount and currency have defined meanings, expected records arrived, and corrections are represented deliberately. These are different checks from whether the compute process exited successfully.

dbt data tests, for example, express assertions about data such as uniqueness, non-null values, and relationships. They are useful building blocks; a passing set of assertions only proves the conditions that were actually checked.

Make freshness, ownership, lineage, and known limitations easy to find next to the output. Access should have an explicit purpose and a manageable lifecycle. A dataset becoming available inside the platform should not automatically make it available to every downstream system.

Data contracts label the ingredients; dbt models prepare the result.

A data contract is the producer’s promise about a dataset: its columns, meanings, ownership, freshness, and how changes are handled. For a child-friendly example, a box labelled “12 apples” should contain apples, not oranges. For payments, “amount” must say whether 100 means one krone or one hundred kroner.

See the payment event contract

This is an illustrative producer-contract schema. A validator and runtime checks must implement its promises; writing a field called checks does not run a test.

# contracts/payment-events.yaml — fictional producer contract
name: payment_events
version: 1
owner: payments-team
freshness: available by 05:30 Europe/Oslo each day
columns:
  - name: payment_id
    type: string
    meaning: Stable identifier; repeated deliveries use the same value
    checks: [not_null, unique]
  - name: event_time
    type: timestamp
    meaning: When the payment happened, in UTC
  - name: amount_minor
    type: bigint
    meaning: Amount in the currency's minor unit; 100 means 1 NOK
  - name: currency
    type: string
    meaning: Three-letter currency code
change_policy: Review breaking changes with consumers before deployment

A dbt model is a SQL query saved in a file. This one turns individual payments into daily totals, keeping currencies separate. dbt uses the model to build a table or view, according to its materialisation configuration.

See the dbt model and its YAML tests
-- models/daily_totals.sql
-- Run with the SQL session timezone set to UTC.
-- One row per UTC day and currency; never mix currencies.
select
  cast(event_time as date) as payment_date,
  currency,
  sum(amount_minor) as total_amount_minor
from {{ source('payments', 'payment_events') }}
group by cast(event_time as date), currency
# models/daily_totals.yml — dbt model documentation and tests
version: 2
models:
  - name: daily_totals
    description: Daily payment totals, kept separate by currency
    columns:
      - name: payment_date
        data_tests: [not_null]
      - name: currency
        data_tests: [not_null]
      - name: total_amount_minor
        data_tests: [not_null]

The source must also be declared in the dbt project. The platform schedules dbt build --select daily_totals under its job identity. These tests check for missing values; they do not prove completeness, correct deduplication, or correct business totals. Those need additional assertions and source checks.

The SQL is reviewed alongside the YAML. A producer contract covers the wider promise between teams; a dbt model contract can additionally enforce an output’s column names and types when configured. Documentation, contract enforcement, and data-quality tests solve related but different problems.

06 / DESIGN FOR TIME AND FAILURE

The arrows need more than a direction.

“Data moves from A to B” hides important behaviour. Does the job append records, update existing ones, or replace the whole table? What happens after a missed day? What happens when an old event arrives twice?

Recovery should be a normal operation. Keep the inputs needed for the promised recovery window, record progress, and design retries to avoid applying the same logical change twice. Where source retention, privacy, or deletion rules prevent replay, document the boundary instead of promising unlimited recovery.

A practical runbook should explain how to identify the affected range, correct the cause, reprocess that range, validate the output, and tell consumers when it is trustworthy again. Delta Lake’s batch documentation describes mechanisms such as idempotent writes and historical reads. Those mechanisms still need an end-to-end recovery design, including retention and downstream effects.

07 / KEEP IT USEFUL TO OPERATE

Measure the promises people depend on.

I would rather see a small set of meaningful service measures than a wall of green infrastructure charts. How long does it take a team to publish its first useful dataset? Are consumers getting fresh enough data? Can an owner explain a failed delivery and recover it? Can costs be attributed to a workload?

Set targets from the use case. A daily report and an interactive feature need different delivery guarantees. Faster processing has little value when the source arrives once a day; a cheap daily batch is no bargain when the product requires timely updates.

Maintenance belongs in the product too: remove unused datasets, retire duplicate paths, keep dependencies understandable, and make ownership survive people changing teams.

The platform should become easier to use as it grows. That takes deliberate work on defaults, documentation, and the paths you choose to retire.

A PRACTICAL REVIEW

Try it with one real consumer.

Before adding another service or drawing another architecture diagram, walk one delivery through these questions:

  1. Use: What decision or product behaviour does this output enable?
  2. Meaning: Are identifiers, timestamps, updates, and business definitions explicit?
  3. Ownership: Who answers when the source changes or the output breaks?
  4. Access: Are the human approval path, workload identity, and effective Unity Catalog grants explicit?
  5. Delivery: Are jobs, infrastructure, and access declared in YAML, reviewed, planned and applied with Terraform/OpenTofu through GitHub Actions?
  6. Trust: Can a consumer see freshness, quality checks, and limitations?
  7. Recovery: Can we correct a bad range and verify the result?
  8. Cost: Can we explain the operating cost and retire the output when it is no longer useful?

Clear answers are a better starting point than a longer list of tools. Build the smallest dependable path, learn from the people using it, and improve the parts that slow them down.
