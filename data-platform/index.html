What makes a
good data platform?

Teams can build on each other’s models and safely bring shared and external data into products. Each contribution makes the next easier, so the value compounds.

By Isak Rathe Støre · Updated 12 November 2026 · About 10 minutes

01 / START WITH THE USE

Follow one temperature signal.

Sensor A in vehicle 42 reports 4.2°C, then 4.4°C, then 4.8°C. Is it warming, or is the data misleading?

Follow those readings into a shared table, through useful SQL and reusable models, then back into the delivery app.

02 / MAKE THE NORMAL PATH EASY

Build supported workflows from repeated needs.

Supported workflows turn configuration into infrastructure. The transport team declares its sensor feed; the platform builds the storage, jobs, identities and permissions.

Configuration defines infrastructure, access, jobs, runtime locations and code deployment. Teams supply their business logic; the platform automates the surrounding setup.

Supported choices are deliberately limited. The platform team maintains the building blocks; teams own their source data and product logic.

When the same need appears repeatedly, turn it into another supported workflow. Handle unusual requests through a supported extension or an explicitly owned exception.

Reference · Who owns each part?

Publish beyond Databricks, and build on the platform.

Later, the temperature-status model can feed a delivery app beyond Databricks. Its supported publication path declares the destination, access and delivery expectations.

Teams receive two software identities: a deployer to create or update resources, and a runner to execute jobs and access data.

Within those permissions, teams manage their own infrastructure, configuration and code for dashboards, data science, MLflow models, jobs and other supported resources.

External data needs an internal owner. That team owns permitted use, mapping, freshness and the response to provider changes.

A field changes meaningThe producer explains the change and coordinates the contract with consumers.
A shared connector stopsThe platform team repairs the delivery mechanism and coordinates recovery with the source owner.
A product total is wrongThe product team checks its transformation and traces the inputs with the producer and platform.
03 / WRITE DOWN THE RECIPE

YAML describes it. Terraform or OpenTofu builds it.

YAML is the order form. It declares the desired setup in readable text, kept in GitHub alongside the code.

Terraform or OpenTofu builds the infrastructure. Platform modules translate YAML into resources, jobs and Unity Catalog grants. Python and SQL implement processing and models.

GitHub Actions runs the delivery. A plan previews changes; an apply carries them out after review and approval.

The quality team wants to investigate warming vehicles. Its configuration names that purpose, an access group and the required datasets.

See the GitHub Actions workflow shape

Illustrative workflow. Installation, federated authentication, provider versions and remote state are assumed configured. The repository-owned validation script checks configuration and creates the pull-request plan.

# .github/workflows/platform.yml — illustrative workflow
name: Validate and deploy platform
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/validate-platform
  deploy:
    if: github.event_name == 'push'
    needs: validate
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      # Authenticate using a configured federated identity.
      - name: Plan and apply merged infrastructure
        working-directory: infrastructure
        run: |
          tofu init -input=false
          tofu validate
          tofu plan -input=false -out=deployment.tfplan
          tofu apply -input=false deployment.tfplan

Pull requests validate and preview changes. After merge, the protected production job creates and applies a fresh plan for that revision.

Configure GitHub environment protection and federated identity separately. A saved plan depends on its configuration and state; do not blindly reuse an older pull-request plan.

Keep infrastructure state in a shared, access-controlled backend with locking. Pin engine and provider versions. Terraform uses the same plan/apply structure as the OpenTofu example.

04 / GIVE EACH IDENTITY THE RIGHT KEYS

Finding a table is different from being allowed to read it.

Unity Catalog is the data directory and permission system. published.transport.temperature_readings identifies a catalog, schema and table.

Reading requires USE CATALOG, USE SCHEMA and table SELECT. Container access alone does not allow row reads.

The analyst needs the shared readings. Both public and non-public data are explorable; non-public access is provisioned to a purpose-based Entra group.

After approved group membership, the analyst explores vehicle 42 with SQL. Agents can help write the query; execution still requires the caller’s effective permissions.

A pull request approves the offered access. Access management approves who receives it, for what purpose and duration.

See YAML become Terraform-managed Unity Catalog grants

The Databricks databricks_grants resource turns the project’s approved access into Terraform-managed permissions.

Illustrative extension for one requested table. A full module handles every table and supplies authentication, existing resources and group provisioning.

# consumers/analytics-projects/quality_optimization.yaml — excerpt
access_group: team-quality-optimization
table_access:
  - name: published.transport.temperature_readings
# access.tf — simplified platform module
locals {
  project = yamldecode(file("${path.module}/../consumers/analytics-projects/quality_optimization.yaml"))
  # Show one requested table; a full module handles every table_access entry.
  access = {
    catalog       = "published"
    schema        = "transport"
    table         = "temperature_readings"
    readers_group = local.project.access_group
  }
}

resource "databricks_grants" "catalog" {
  catalog = local.access.catalog
  grant {
    principal  = local.access.readers_group
    privileges = ["USE_CATALOG"]
  }
}

resource "databricks_grants" "schema" {
  schema = "${local.access.catalog}.${local.access.schema}"
  grant {
    principal  = local.access.readers_group
    privileges = ["USE_SCHEMA"]
  }
}

resource "databricks_grants" "table" {
  table = "${local.access.catalog}.${local.access.schema}.${local.access.table}"
  grant {
    principal  = local.access.readers_group
    privileges = ["SELECT"]
  }
}

USE_CATALOG and USE_SCHEMA allow container use; SELECT permits reads. Approved group members inherit these grants.

databricks_grants manages an object’s full grant set. Collect all intended principals in one place; competing resources or manual edits can overwrite permissions.

A direct service-principal grant uses its registered application identifier. A group grant uses the account-group name. Both follow the reviewed infrastructure process.

A service principal identifies software. An Azure managed identity avoids an application-managed password. Both still need provisioning and permissions; a storage connector’s identity is separate from a job runner.

Verify workspace, compute, storage and destination permissions too. An export needs source-read and destination-write access. Revocation must account for other groups and direct grants.

05 / MAKE TRUST INSPECTABLE

A green job is only the beginning.

A rising chart can mislead if readings are duplicated, late or in the wrong unit. Check timestamps, Celsius values and missing intervals.

Show ownership, lineage, quality checks and limitations beside each dataset. Publication inside the platform does not automatically approve every downstream use.

Define the contract. Test the model.

A data contract defines columns, meaning, ownership, freshness and change rules. A temperature reading needs a unit, timestamp and vehicle identifier.

A dbt model saves useful SQL as a reusable table or view. Start with each vehicle’s average temperature per minute.

See a dbt extension to the transport example

The public repository defines the source data. This model and its tests are additional teaching examples, not files already implemented there.

-- models/minute_vehicle_temperatures.sql — illustrative extension
-- Use UTC for the SQL session timezone.
select
  date_trunc('minute', measurement_time) as measurement_minute,
  vehicle_id,
  avg(temperature_celsius) as average_temperature_celsius
from {{ source('transport', 'temperature_readings') }}
group by date_trunc('minute', measurement_time), vehicle_id
# models/minute_vehicle_temperatures.yml — illustrative extension
version: 2
models:
  - name: minute_vehicle_temperatures
    description: Average sensor temperature per minute and vehicle
    columns:
      - name: measurement_minute
        data_tests: [not_null]
      - name: vehicle_id
        data_tests: [not_null]
      - name: average_temperature_celsius
        data_tests: [not_null]

Declare the source and schedule the model under its runner identity. These tests check missing values, not completeness or duplicates.

A minute average can still hide brief spikes. Keep the raw readings available for investigation within the agreed retention window.

Review SQL alongside YAML. Producer contracts describe the promise; dbt contracts enforce configured columns and types; data tests check selected quality conditions.

A second model reads minute_vehicle_temperatures and finds warm periods using a configured limit. A third turns those periods into a status.

Teams reuse these models instead of copying the original query. The limit, treatment of missing readings and freshness remain explicit parts of the contract.

06 / DESIGN FOR TIME AND FAILURE

The arrows need more than a direction.

What if sensor A sends the same reading twice, or reconnects after an hour? Define updates, missing intervals and replay before trusting the status.

Reference · Delivery modes

Retain inputs for the agreed recovery window. Record progress and make retries avoid duplicate changes. State where privacy, deletion or source retention limits replay.

If readings were wrong, fix the cause and reprocess the affected range. Rebuild dependent models, validate the status and tell consumers when it is trustworthy.

07 / KEEP IT USEFUL TO OPERATE

Measure the promises people depend on.

Can the app tell whether vehicle 42’s status is fresh? Measure source-to-product delay, recovery and attributable cost.

Set targets from the use case. A daily report and an interactive feature need different delivery guarantees.

Retire unused datasets and duplicate paths. Keep dependencies clear and ownership current as people change teams.

08 / HELP PEOPLE AND INVESTIGATE FAILURES

Give agents useful tools and people clear ownership.

If the temperature status stops updating, people and agents can investigate together in Slack, using the same runbooks and source evidence.

The harness is the agent’s toolbox and operating setup: instructions, context, tools, identity and limits.

For a failed job, check existing investigations, inspect permitted evidence and explain the likely cause. A proposed fix follows the normal pull-request review process.

Alerts grant no extra permissions. Agents should cite evidence, ask when facts are missing, and stand back when a person takes over.

Technical detail · Deploy and operate the agent harness

Package the harness in a container. GitHub Actions deploys it to Kubernetes; Terraform manages supporting resources and grants.

Use separate test/production configuration, workload identity and secret references.

An authenticated interface, such as Model Context Protocol, connects Slack to a specialist agent. The specialist retains its own permissions.

Example · Describe the harness and its boundaries

Illustrative design YAML, not a configuration schema implemented by the public example repository. The deployment and identity system must enforce these choices.

agent:
  purpose: explain failed data deliveries and propose repairs
  inputs:
    - approved Slack support channels
    - approved failure notifications
  evidence:
    - versioned runbooks and source repositories
    - job status and logs allowed by the workload identity
  outputs:
    - an evidence-backed reply in the original thread
    - a fix pull request where repository write access is approved
  change_path: pull request, review, deployment approval
  runtime:
    package: versioned container image
    environments: [test, production]
    identity: workload identity
    credentials: secret references
    limits: bounded context, tool calls and execution time

Monitor tool failures, queue time and answer quality. Test real investigations, recovery notices, duplicates and human takeover. A healthy container does not prove useful support.

The app consumes the shared status through an approved publication path. It shows when the result was updated and treats missing or stale data explicitly.

A PRACTICAL REVIEW

Try it with one real consumer.

Walk one delivery through these questions:

  1. Use: What decision or product behaviour does this output enable?
  2. Meaning: Are identifiers, timestamps, updates, and business definitions explicit?
  3. Ownership: Who answers when the source changes or the output breaks?
  4. Access: Are the human approval path, workload identity, and effective Unity Catalog grants explicit?
  5. Delivery: Are YAML changes reviewed and deployed through GitHub Actions and Terraform/OpenTofu?
  6. Trust: Can a consumer see freshness, quality checks, and limitations?
  7. Recovery: Can we correct a bad range and verify the result?
  8. Support: Can people and agents investigate failures and propose reviewed fixes?
  9. Cost: Can we explain the operating cost and retire the output when it is no longer useful?
